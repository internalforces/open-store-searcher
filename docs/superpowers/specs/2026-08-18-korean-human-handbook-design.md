# Korean Human Handbook Design

_Last updated: 2026-08-18_

## 1. Decision Summary

Create a Korean-language project handbook under `handbook/ko/` for people who need to understand the project. Treat the handbook as explanatory output rather than an implementation input.

Implementation roles must not read, search, summarize, cite, or use `handbook/ko/**` while planning, implementing, testing, or reviewing product changes. The Documenter may access it only during the milestone-close documentation pass or when a human explicitly requests handbook work.

The English harness, source PRD, accepted ADRs, active task, implementation, tests, and verification evidence remain the sources of truth.

## 2. Goals

- Give Korean-speaking readers a coherent explanation of the product, architecture, data handling, search behavior, operations, and limitations.
- Keep human-oriented explanations separate from AI governance and implementation context.
- Update the handbook from verified outcomes after every milestone.
- Make the handbook's baseline milestone, review date, and non-authoritative status visible.
- Prevent planned or unverified behavior from being described as implemented behavior.

## 3. Non-Goals

- The handbook does not replace the PRD, ADRs, tasks, tests, reports, or English harness memory.
- The handbook is not part of the mandatory implementation context-loading order.
- The handbook does not introduce requirements, status mappings, architecture decisions, or release authority.
- The handbook is not generated by automatic translation.
- This design does not create a second repository, documentation site, or external service.

## 4. Repository Boundary

Use this structure:

```text
handbook/
└── ko/
    ├── README.md
    ├── project-overview.md
    ├── architecture.md
    ├── data-and-status.md
    ├── search-and-ui.md
    ├── operations.md
    ├── glossary.md
    └── milestone-history.md
```

Do not place these documents under `docs/`. The existing `docs/` directory contains harness references and traceability records that AI roles use during implementation.

The root `README.md`, public policies, contributor documentation, and release documentation planned for M3 remain separate deliverables. They may link to the handbook after their audience and language policy are approved, but the handbook does not replace them.

## 5. Access and Authority Rules

Add the following policy to the English project constitution:

1. `handbook/ko/**` is human-facing explanatory documentation and is not harness content.
2. Planner, Architect, Researcher, Implementer, Debugger, Tester, Reviewer, Security Reviewer, Performance Engineer, and Release Manager must not load or use handbook content during implementation workflows.
3. Repository-wide searches used for implementation must exclude `handbook/ko/**`.
4. The Documenter may read and update the handbook only after a milestone has met its code, test, and review gates, or when a human explicitly requests handbook work.
5. Handbook content cannot resolve ambiguity or override the PRD, an ADR, an active task, tests, verification evidence, or the project constitution.
6. If a handbook statement conflicts with an authoritative source, correct the handbook during a documentation pass; do not change implementation to match the handbook.

The restriction is a governance boundary enforced through `AGENTS.md`, role prompts, workflow routing, and review checklists. Generic ignore files are not sufficient because AI tools do not share a guaranteed ignore-file standard.

## 6. Document Set

### `README.md`

Provide the handbook purpose, intended audience, navigation, current baseline milestone, last human review date, and a prominent statement that the handbook is not an implementation specification.

### `project-overview.md`

Explain the problem, intended users, supported region, core workflow, product scope, non-goals, zero-cost boundary, privacy model, and the distinction between administrative status and real-time opening status.

### `architecture.md`

Explain the static architecture, build-time data processing, GitHub Pages delivery, browser-side search, trust boundaries, major components, and end-to-end data flow. Prefer a small diagram over a code-oriented module inventory.

### `data-and-status.md`

Explain official data sources, attribution, as-of dates, record transformation, raw and processed statuses, uncertainty handling, validation, new source codes, stale-data warnings, and last-known-good preservation.

### `search-and-ui.md`

Explain input normalization, candidate ranking, name and address conflicts, confidence, empty results, keyboard and screen-reader behavior, and external verification links without presenting the algorithm as more certain than it is.

### `operations.md`

Explain refresh scheduling, validation gates, publication, recovery, delayed data, deployment boundaries, and the operational meaning of a failed refresh. Include procedures only after they have been verified.

### `glossary.md`

Define project-specific terms in Korean, including exact product and source-system literals whose spelling matters. Link to the detailed document instead of duplicating policy explanations.

### `milestone-history.md`

Record each completed milestone's date, delivered capabilities, important accepted decisions, known limitations, documentation changes, and verification status. Do not copy task-by-task implementation logs.

## 7. Required Document Header

Every Korean handbook document begins with a visible metadata block equivalent to:

```markdown
> Audience: People who want to understand the project
> Implementation input: No
> Baseline milestone: M0 (replace with the latest completed milestone)
> Last reviewed: YYYY-MM-DD
> Status: Describes verified implementation at the stated milestone
```

The actual handbook renders these labels and explanations in Korean. The metadata must not claim a milestone that has not passed its completion gates.

## 8. Writing Rules

- Write for a person learning the project, not for an implementation agent.
- Describe verified current behavior before background or future plans.
- Clearly label incomplete, deferred, unsupported, and uncertain behavior.
- Explain reasons and limitations rather than copying file trees or internal task records.
- Link to one explanation instead of duplicating text across handbook files.
- Do not expose secrets, credentials, private paths, unpublished security details, or sensitive operational data.
- Preserve the exact meanings of `행정상 영업`, `휴업`, `폐업`, and `확인되지 않음`.
- State that `행정상 영업` is not evidence that a location is open at the current moment.
- State that an empty search result is not evidence that a business is closed.
- Show the data as-of date and the need for additional verification where relevant.
- Do not describe proposals, placeholders, or planned acceptance criteria as completed behavior.

## 9. Milestone-Close Workflow

Add a documentation pass after implementation, testing, and review, but before final milestone closure:

```text
Milestone implementation complete
  → Tests and role reviews complete
  → Planner identifies handbook impact
  → Documenter reads authoritative outcomes and affected handbook files
  → Documenter updates affected Korean documents
  → Documenter records the milestone history entry
  → Human reviews Korean clarity and accuracy
  → Planner records changed or reviewed-without-change documents
  → Milestone closes
```

For each handbook file, the close record must state either:

- Updated, with the reason and review evidence; or
- Reviewed without change, with the reason.

The Documenter must derive content from accepted decisions, completed implementation, passing verification, and Reviewer findings. Work in progress must not be included in the milestone baseline.

## 10. Milestone Coverage

| Milestone | Minimum handbook action |
|---|---|
| M0 | Create the index, project overview, architecture baseline, glossary, and first history entry. |
| M1 | Add data and status documentation; update architecture, operations, glossary, and history. |
| M2 | Add search and UI documentation; update overview, architecture, glossary, and history. |
| M3 | Complete operations and public-release explanations; review the entire handbook and record release readiness. |
| M4 and later | Update every affected document and add one concise milestone history entry. |

Creating an empty future-facing file is optional. If a topic has no verified implementation yet, the index should mark it as unavailable rather than populate it with plans.

## 11. Required Harness Changes

Implementation planning for this design must cover these minimal changes:

- `AGENTS.md`: define the handbook exception to the English harness policy, access prohibition, source-of-truth rule, and Documenter exception.
- `ORCHESTRATOR.md`: add the milestone-close documentation pass and human Korean-language review gate.
- `roadmap.md`: add handbook review as a completion condition for every milestone.
- `prompts/documentation.md`: define when the Documenter may access the handbook and how verified outcomes are translated into human explanations.
- Role prompts used during implementation and review: add a concise prohibition against loading `handbook/ko/**`.
- `docs/README.md`: list the handbook boundary and access rule without duplicating its Korean contents.
- `tasks/backlog.md`: add recurring milestone handbook work or revise documentation task routing so it is not deferred entirely to M3.
- `memory/decisions.md`: record the accepted handbook boundary and milestone-update policy.
- `handbook/ko/**`: create only the documents justified by the current completed milestone.

## 12. Verification

Verify the implementation of this design with checks that:

- all handbook Markdown is contained under `handbook/ko/`;
- no implementation context-loading list links to a handbook content file;
- implementation prompts explicitly exclude `handbook/ko/**`;
- the Documenter prompt grants only milestone-close or explicitly requested access;
- each existing milestone has a handbook completion or review criterion;
- every created handbook file has the required audience, implementation-input, baseline, review-date, and status metadata;
- Korean safety terminology remains exact and its limitations are stated;
- no handbook statement presents an unresolved placeholder as fact;
- milestone history matches completed tasks and verification evidence;
- Markdown links and code fences are valid.

## 13. Risks and Mitigations

### AI agents read the handbook accidentally

Mitigate through explicit constitutional rules, role-prompt exclusions, search exclusions, and review checks. Use a separate repository only if policy-level isolation later proves insufficient.

### The handbook becomes a competing source of truth

Mitigate by displaying its explanatory status, baseline milestone, and authority boundary in every document and by resolving conflicts in favor of authoritative project records.

### Documentation drifts between milestones

Mitigate by showing the baseline milestone and last review date. The handbook may intentionally lag work in progress, but it must not appear current beyond its declared baseline.

### Automatic translation changes safety meaning

Mitigate by requiring curated Korean writing and human review, especially for status, uncertainty, and data-freshness language.

### Documentation work delays milestone closure

Mitigate by updating only affected documents and recording explicit reviewed-without-change outcomes for the rest.

## 14. Acceptance Criteria

- The handbook has a dedicated `handbook/ko/` boundary distinct from harness `docs/`.
- Korean handbook content is formally exempted from the English-only harness rule because it is not harness content.
- Implementation roles are prohibited from using handbook content as context or evidence.
- The Documenter exception is limited to milestone-close work or explicit human requests.
- Every milestone includes an affected-document review before final closure.
- Every handbook file identifies its audience, non-authoritative role, baseline milestone, and review date.
- Handbook updates describe verified outcomes and preserve all product safety invariants.
- Human review is required before the milestone documentation gate passes.
