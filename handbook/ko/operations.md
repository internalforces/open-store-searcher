# 운영

> 대상: 데이터 갱신, 배포와 장애 대응 원칙을 이해하려는 사람
> 구현 입력: 아니오
> 기준 상태: M0 구현·기술 검증 완료 — 데이터 갱신과 배포 운영 전
> 최종 검토일: 2026-08-24
> 상태: 실행 가능한 개발·검증 기반과 아직 계획 단계인 운영 절차를 구분해 설명함

## 현재 운영 상태

최소 정적 애플리케이션과 개발·테스트·빌드 명령은 실행할 수 있다. 그러나 사업체 데이터 갱신 작업, 실제 검색 기능, GitHub Actions 배포 워크플로와 운영 URL은 아직 없다.

따라서 이 문서는 배포된 서비스의 운영 절차서가 아니다. M0에서 검증된 개발 기반과 앞으로 데이터·배포 운영이 지켜야 할 승인된 원칙을 함께 설명한다.

## M0에서 검증한 개발 명령

승인된 환경은 Node.js 24.19.0 LTS와 npm 11.17.0이다. 정확한 의존성은 잠금 파일로 고정한다.

| 목적 | 명령 | 현재 의미 |
|---|---|---|
| 의존성 설치 | `npm ci` | 잠금 파일과 동일한 의존성을 설치 |
| 개발 화면 실행 | `npm run dev` | 최소 정적 화면을 개발 서버에서 확인 |
| 정적 빌드 | `npm run build` | GitHub Pages에 올릴 수 있는 정적 산출물을 생성 |
| 빌드 미리보기 | `npm run preview` | 생성한 정적 산출물을 로컬에서 확인 |
| 빠른 검증 | `npm run verify` | 코드·형식·타입·빌드·Vitest 검사를 실행 |
| 전체 검증 | `npm run verify:full` | 빠른 검증에 브라우저와 자동 접근성 검사를 추가 |

M0 기술 기반 검증에서는 현재 존재하는 컴포넌트 테스트가 네 가지 Vitest 지표에서 100%를 기록했고, 데스크톱 Chromium·Firefox·WebKit과 모바일 Chromium의 하위 경로 화면 검사가 통과했다. 데스크톱·모바일 Chromium의 자동 접근성 검사도 위반 0건으로 통과했다. 이 수치는 현재 최소 화면과 테스트 대상에 대한 결과이며, 앞으로 구현할 검색 제품 전체의 품질이나 접근성을 보장하지 않는다.

## 계획된 갱신 흐름

```text
하루 한 번 변경 확인
  → 공식 원천 데이터 다운로드
  → 변경이 있을 때만 변환
  → 스키마·품질·상태·크기 검증
  → 모든 검증 통과
  → 정적 JSON과 사이트 게시
  → 배포 상태와 데이터 기준일 확인
```

정확한 스케줄, 다운로드 방법과 워크플로 권한은 데이터 계약과 배포 설계가 승인된 뒤 확정한다.

## 게시 안전 원칙

- 원천 데이터가 바뀌지 않았다면 불필요한 산출물 생성을 피한다.
- 필수 필드, 상태 코드, 중복, 급격한 레코드 수 변화, 기준일과 파일 크기를 검사한다.
- 일부 검사만 통과한 데이터를 게시하지 않는다.
- 모든 산출물을 완전히 검증한 뒤 한 단위로 교체한다.
- 검증에 실패하면 마지막 정상 데이터를 계속 제공한다.
- 실패 원인과 마지막 정상 갱신 시점을 사람이 확인할 수 있게 남긴다.

마지막 정상 데이터 보존은 설계 원칙만으로 충분하지 않다. 실제 배포 방식에 대한 실패 주입 테스트를 통과해야 한다.

## 예상 실패와 대응 방향

| 상황 | 대응 원칙 |
|---|---|
| 원천 다운로드 실패 | 새 데이터를 게시하지 않고 이전 정상 데이터 유지 |
| 필수 열 또는 스키마 변경 | 검증 실패로 중단하고 변경 내용을 조사 |
| 새로운 상태 코드 발견 | 임의 매핑을 금지하고 승인 전까지 불확실하게 처리 |
| 레코드 수 급감·급증 | 이상 변화로 중단하고 원천과 변환 과정을 확인 |
| JSON 형식 또는 크기 문제 | 게시를 중단하고 이전 산출물 유지 |
| 갱신 장기 지연 | 화면에 기준일과 오래된 데이터 경고 표시 |
| 정적 사이트 로딩 실패 | 새로고침과 이슈 제보 경로 안내 |

구체적인 재시도 횟수, 보관 위치와 복구 명령은 아직 정해지지 않았다.

## 배포와 승인

기본 배포 대상은 GitHub Pages이며 GitHub Actions가 정적 산출물을 만든다. 다음 작업에는 사람이 승인해야 한다.

- 최초 언어·프레임워크·패키지 관리자와 저장소 구조 선택
- 외부 의존성 또는 서비스 추가
- 원천 데이터 제공 방식과 상태 매핑 변경
- GitHub Actions 권한, Pages 배포 방식과 인프라 변경
- 보안 관련 수정
- 공개 URL이나 공유 식별자 형식 변경
- 릴리스 태그 생성과 모든 배포

현재는 배포 승인을 요청할 단계가 아니다. GitHub Pages 하위 경로 형태의 정적 빌드는 로컬 미리보기에서 검증했지만 실제 GitHub Actions 배포 설정과 공개 URL은 만들지 않았다.

## 권한과 공급망

GitHub Actions 권한은 필요한 범위로 최소화해야 한다. 외부 Action을 사용할 경우 정확한 버전과 공급망 위험을 검토하고 가능하면 변경되지 않는 커밋 식별자로 고정한다. 다운로드 파일은 스키마뿐 아니라 비정상적인 압축과 크기 위험도 확인해야 한다.

구체적인 워크플로가 만들어지면 Security Reviewer의 검토와 사람 승인을 받아야 한다.

## 비용 원칙

기본 배포에는 필수 월 비용과 결제수단 등록이 없어야 한다. GitHub Pages, 공개 저장소의 표준 GitHub Actions 실행 범위와 정적 파일을 사용한다. 사용자 지정 도메인은 선택사항이며 기본 운영 조건이 아니다.

무료 플랫폼 정책이나 한도가 바뀌면 정적 웹 자산을 다른 무료 호스팅으로 옮길 수 있어야 한다. 새로운 서비스 채택은 비용·라이선스·개인정보·유지보수 위험을 함께 검토한다.

## 개인정보와 보안

- 검색어, 클릭, 위치와 사용 행동을 수집하거나 저장하지 않는다.
- 분석, 광고와 추적 스크립트를 넣지 않는다.
- 사용자 입력과 원천 데이터는 HTML로 실행하지 않고 텍스트로 표시한다.
- 비밀값과 API 키를 정적 번들, 로그와 저장소에 넣지 않는다.
- 외부 지도 링크는 사용자가 클릭했을 때만 이동한다.

## 마일스톤 종료와 문서

각 마일스톤의 구현·테스트·검토가 완료된 뒤 운영 변화가 있으면 이 문서를 갱신한다. 실행해 검증하지 않은 명령이나 복구 절차는 운영 절차처럼 작성하지 않는다. 변경이 없더라도 검토 결과를 마일스톤 기록에 남기고, 사람이 한국어 설명을 최종 확인한 뒤 마일스톤을 닫는다.
