## Trigger and privilege boundaries

`verify.yml` accepts pull requests and main pushes. Fork code has only a job-scoped
`contents: read` token and no configured secrets; checkout disables credential persistence.
`refresh.yml` accepts schedule/manual events and restricts preparation to the default branch.
No `pull_request_target`, `workflow_run`, fork-ref input or cross-run artifact consumption exists.
Manual bootstrap is a boolean passed through an environment variable, never a shell fragment.

Both workflows deny permissions by default. Preparation has only `contents: read`; Pages write
and OIDC exist only in the dependent deploy job. That job additionally has `contents: read`
for a Git ref check after environment approval, then executes the pinned deployment action
without checking out or building source. There is no contents write, PAT, secret file, package
publication or paid runtime service. Contextual commit/branch values go through environment
variables and quoted shell arguments, not `${{ }}` interpolation into shell source.

All top-level actions are pinned to verified official tag commit SHAs; see the
[verification report](test-2026-09-12-task-009-010.md). This statement is limited to references
in these two files; it is not a recursive supply-chain audit of bundled/composite action code.
No new npm dependency was added. The Pages artifact comes from the same trusted run only after
validation and build steps succeed. Failure cannot advance a separately stored baseline:
baseline metadata is packaged with the site and read back with descriptor/hash consistency checks.
